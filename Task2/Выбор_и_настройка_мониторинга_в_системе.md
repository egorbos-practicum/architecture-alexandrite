# Выбор и настройка мониторинга в системе

## 1. Мотивация

**Проблемы бизнеса, которые решает мониторинг:**

- Потеря клиентов и контрактов - Мониторинг позволит проактивно обнаруживать проблемы до того, как они приведут к потере клиентов.
- Рост жалоб и недовольства пользователей - Реальный мониторинг покажет, где именно возникают задержки и ошибки, вместо того чтобы полагаться на жалобы как основной источник информации о проблемах.
- Простои и задержки в производстве - Мониторинг MES поможет выявить узкие места в работе операторов и ускорить выполнение заказов.
- Неэффективное использование ресурсов - Без метрик невозможно определить, где реальные проблемы с производительностью, а где восприятие пользователей.

**Что даст внедрение мониторинга:**

- Снижение времени обнаружения проблем с часов/дней до минут
- Возможность планировать масштабирование на основе реальных данных, а не предположений
- Объективные метрики для оценки эффективности оптимизаций
- Раннее предупреждение о потенциальных сбоях
- Снижение нагрузки на поддержку за счет автоматического обнаружения проблем

**ROI для бизнеса:**

- Предотвращение потери контрактов (один крупный контракт стоит больше, чем год затрат на мониторинг)
- Увеличение скорости выполнения заказов (ускорение cash flow)
- Улучшение удовлетворенности клиентов (повышение retention)
- Оптимизация инфраструктурных затрат

## 2. Выбор подхода к мониторингу

**Комбинированный подход для разных слоев системы:**

**Для пользовательских интерфейсов (Интернет-магазин, CRM, MES):**

Методология RED (Rate, Errors, Duration) - так как мы отслеживаем веб-приложения<br>
*Фокус:* пользовательский опыт, время загрузки страниц, успешность операций

**Для API и микросервисов (Shop API, CRM API, MES API):**

Четыре золотых сигнала - так как это backend-сервисы<br>
Latency, Traffic, Errors, Saturation - полное покрытие работы API

**Для инфраструктуры (Базы данных, Очереди, Хранилища):**

Методология USE (Utilization, Saturation, Errors) - для ресурс-ориентированных компонентов<br>
*Фокус:* утилизация ресурсов, предотвращение saturation

**Для бизнес-процессов:**

Ключевые бизнес-метрики - мониторинг сквозных процессов<br>
*Примеры:* время выполнения заказа, конверсия, статусы заказов

**1. Метрики для отслеживания**

Группа 1: Четыре золотых сигнала для API

1.1 Задержка (Latency)

Зачем: Измерение времени ответа API критично для пользовательского опыта<br>
Метрики:

    api_response_time_ms{p50, p95, p99} - перцентили времени ответа
    api_request_duration_seconds_bucket - гистограмма времени ответа
    Ярлыки: endpoint, method, status_code, service, env

1.2 Трафик (Traffic)

Зачем: Понимание нагрузки и выявление аномалий<br>
Метрики:

    api_requests_total - общее количество запросов
    api_requests_per_second - RPS по эндпоинтам
    Ярлыки: endpoint, method, service, env

1.3 Ошибки (Errors)

Зачем: Отслеживание стабильности и доступности<br>
Метрики:

    api_errors_total - количество ошибок
    api_error_rate - процент ошибок
    http_requests_total{status!~"2.."} - не-2xx ответы
    Ярлыки: endpoint, method, status_code, error_type, service, env

1.4 Насыщенность (Saturation)

Зачем: Предотвращение перегрузки сервисов<br>
Метрики:

    system_cpu_usage - использование CPU
    jvm_memory_used_bytes - использование памяти
    thread_pool_active_threads - активные потоки
    Ярлыки: service, host, env

Группа 2: Метрики бизнес-процессов

2.1 Статусы заказов

Зачем: Мониторинг потока заказов через систему<br>
Метрики:

    orders_by_status - количество заказов по статусам
    order_status_transitions_total - переходы между статусами
    Ярлыки: status, source_system, env

2.2 Время выполнения операций

Зачем: Выявление задержек в бизнес-процессах<br>
Метрики:

    order_processing_duration_seconds - время обработки заказа
    price_calculation_duration_seconds - время расчёта стоимости
    manufacturing_duration_seconds - время производства
    Ярлыки: order_type, complexity, operator_id, env

2.3 Конверсия и успешность

Зачем: Отслеживание бизнес-эффективности<br>
Метрики:

    cart_to_order_conversion_rate - конверсия корзины в заказ
    order_success_rate - процент успешных заказов
    api_client_success_rate - успешность API-клиентов
    Ярлыки: client_type, source, env

Группа 3: Метрики инфраструктуры (USE)

3.1 База данных (PostgreSQL)

Зачем: Мониторинг производительности и доступности БД<br>
Метрики:

    postgresql_connections_active - активные соединения
    postgresql_transactions_per_second - TPS
    postgresql_query_duration_seconds - время выполнения запросов
    postgresql_locks_total - блокировки
    postgresql_replication_lag_bytes - лаг репликации
    Ярлыки: database, table, query_type, host, env

3.2 Очередь сообщений (RabbitMQ)

Зачем: Отслеживание надёжности обмена сообщениями<br>
Метрики:

    rabbitmq_queue_messages - сообщения в очередях
    rabbitmq_message_publish_rate - скорость публикации
    rabbitmq_message_deliver_rate - скорость доставки
    rabbitmq_consumers - количество потребителей
    Ярлыки: queue, exchange, vhost, env

3.3 S3-совместимое хранилище

Зачем: Мониторинг доступности и производительности хранилища<br>
Метрики:

    storage_operations_total - операции с хранилищем
    storage_latency_seconds - задержка операций
    storage_errors_total - ошибки хранилища
    storage_usage_bytes - использование дискового пространства
    Ярлыки: operation, bucket, env

Группа 4: Метрики пользовательского опыта (RED)

4.1 Frontend

Зачем: Измерение реального пользовательского опыта<br>
Метрики:

    page_load_time_seconds - время загрузки страниц
    first_contentful_paint_seconds - First Contentful Paint
    largest_contentful_paint_seconds - Largest Contentful Paint
    first_input_delay_seconds - First Input Delay
    Ярлыки: page, device_type, browser, env

4.2 Бизнес-транзакции

Зачем: Мониторинг ключевых пользовательских действий<br>
Метрики:

    user_action_duration_seconds - время выполнения действий
    user_action_success_rate - успешность действий
    user_sessions_total - количество сессий
    Ярлыки: action_type, user_role, env

Группа 5: Дополнительные метрики

5.1 Расчет стоимости (критичный процесс)

Зачем: Мониторинг самого медленного процесса в системе<br>
Метрики:

    price_calculation_queue_length - очередь расчётов
    price_calculation_active_workers - активные воркеры
    price_calculation_success_rate - успешность расчётов
    model_complexity_polygons - сложность моделей (полигоны)
    Ярлыки: calculation_type, model_type, worker_id, env

5.2 SLA/SLO мониторинг

Зачем: Измерение соответствия обязательствам<br>
Метрики:

    slo_availability - доступность сервисов
    slo_latency - соответствие по задержкам
    error_budget_remaining - остаток error budget
    Ярлыки: service, slo_name, env

## 3. План действий

Этап 1: Подготовка (2 недели)

Выбор и настройка стека мониторинга:

- Установка Prometheus для сбора метрик
- Настройка Grafana для визуализации
- Развертывание Alertmanager для уведомлений
- Настройка Loki для централизованных логов

Инструментирование приложений:

- Добавление Prometheus-клиентов в Java-приложения (Micrometer)
- Инструментирование C# приложения (prometheus-net)
- Настройка frontend-метрик через JavaScript SDK
- Установка экспортеров для инфраструктуры (node_exporter, postgres_exporter, rabbitmq_exporter)

Этап 2: Базовый мониторинг (3 недели)

Сбор инфраструктурных метрик:

- Мониторинг серверов (CPU, память, диск, сеть)
- Мониторинг баз данных
- Мониторинг очередей сообщений
- Мониторинг хранилища

Сбор метрик приложений:

- Настройка сбора HTTP-метрик
- Мониторинг бизнес-транзакций
- Отслеживание ошибок и исключений

Этап 3: Расширенный мониторинг (3 недели)

Создание дашбордов:

- Системный дашборд (инфраструктура)
- Дашборды для каждого сервиса
- Бизнес-дашборд (статусы заказов, конверсия)
- Дашборд для расчета стоимости

Настройка алертинга:

- Определение критических метрик
- Настройка пороговых значений
- Настройка уведомлений (email, sms, telegram ...)
- Создание эскалационных политик

Этап 4: Оптимизация и автоматизация (2 недели)

Автоматизация:

- Настройка автообнаружения сервисов
- Автоматическое создание дашбордов
- Интеграция с CI/CD для деплоя конфигураций

Обучение команды:

- Документация по мониторингу
- Обучение использованию дашбордов
- Процедуры реагирования на алерты

## 4. Показатели насыщенности

**Критические показатели насыщенности и пороговые значения:**

5.1 API-сервисы

    Порог: CPU > 80% в течение 5 минут
    Действие: Автоматическое масштабирование (добавление инстансов)
    Эскалация: Если масштабирование не помогает в течение 15 минут, то алерт в канал уведомления и создание инцидента

5.2 Базы данных

    Порог: Активные соединения > 90% от максимума
    Действие: Автоматическое создание read-only реплики
    Эскалация: Если проблема не решена за 10 минут, то звонок DevOps инженеру

5.3 Очередь расчета стоимости

    Порог: Очередь > 100 сообщений или самое старое сообщение > 30 минут
    Действие: Автоматический запуск дополнительных воркеров
    Эскалация: Если очередь продолжает расти, то алерт тимлиду и продакт-менеджеру

5.4 Хранилище 3D-файлов

    Порог: Использование диска > 85%
    Действие: Автоматическая очистка временных файлов старше n (например 7) дней
    Эскалация: Если после очистки > 90%, то автоматическое увеличение диска и алерт DevOps

5.5 Очередь RabbitMQ

    Порог: Длина любой очереди > 1000 сообщений
    Действие: Автоматическое создание алертов для команды разработки
    Эскалация: Если очередь продолжает расти > 5000 сообщений, то остановка приема новых сообщений в проблемную очередь и звонок на дежурного

5.6 SLA-нарушения

    Порог: Error budget < 10% от месячного бюджета
    Действие: Автоматическое создание тикета на заморозку фич и фокус на стабильности
    Эскалация: Если бюджет опускается до 5%, то обязательное совещание архитектора, тимлида и продакт-менеджера

Процедуры реагирования:

Warning (желтый уровень):

    Уведомление команды
    Автоматическое создание задачи в Jira
    Время реакции: 4 часа

Critical (красный уровень):

    Уведомление в канал оповещения команды + SMS на дежурного
    Автоматическое создание инцидента
    Автоматический сбор диагностической информации
    Время реакции: 15 минут

Business Critical (бизнес-критично):

    Все вышеперечисленное + автоматический звонок тимлиду и архитектору
    Автоматическое включение конференции для обсуждения
    Приоритет над всеми другими задачами
    Время реакции: 5 минут

Автоматические действия при насыщении:

    Автомасштабирование: Добавление инстансов при высокой нагрузке
    Троттлинг: Ограничение запросов при приближении к лимитам
    Фолбэк: Включение упрощенных режимов работы
    Перенаправление трафика: Балансировка нагрузки между компонентами
    Аварийное сохранение: Дамп критических данных при угрозе сбоя

Эти показатели и процедуры позволят системе не только обнаруживать проблемы, но и автоматически реагировать на них, минимизируя влияние на бизнес.
