# Архитектурное решение по логированию

## 1. Анализ системы и требования к логированию

**Системы, требующие сбора логов (приоритетные):**

- MES API - расчёт стоимости, назначение операторов
- Shop API - создание заказов, работа с 3D-файлами
- CRM API - управление заказами, интеграция с продавцами
- Базы данных - PostgreSQL (Shop DB, MES DB)
- Message Queue - RabbitMQ
- Frontend приложения - ошибки пользовательского интерфейса

**Критические точки для логирования:**

- Изменения статусов заказов - все переходы между системами
- Ошибки расчёта стоимости - причины неудачных расчётов
- Работа с файлами - загрузка/выгрузка 3D-моделей
- Интеграционные взаимодействия - сообщения между системами
- Аутентификация и авторизация - попытки доступа

## 2. Необходимые логи с уровнем INFO

**1. Изменение статуса заказа**

    timestamp, order_id, old_status, new_status, system, user_id, reason

*Пример:* "2024-01-15T10:30:00Z, ORD-12345, SUBMITTED, PRICE_CALCULATED, MES API, system, automatic"

**2. Создание заказа**

    timestamp, order_id, customer_id, order_type, total_items, source

*Пример:* "2024-01-15T10:15:00Z, ORD-12345, CUST-789, CUSTOM_DESIGN, 1, WEB"

**3. Загрузка 3D-файла**

    timestamp, order_id, file_id, file_size, file_type, success, duration_ms

*Пример*: "2024-01-15T10:20:00Z, ORD-12345, FILE-ABC123, 5242880, .stl, true, 1200"

**4. Расчёт стоимости**

    timestamp, order_id, calculation_id, complexity_score, price, duration_ms, worker_id

*Пример*: "2024-01-15T10:25:00Z, ORD-12345, CALC-456, 85.5, 12500.00, 180000, worker-1"

**5. Работа оператора**

    timestamp, order_id, operator_id, action, previous_status, new_status, duration_minutes

*Пример*: "2024-01-15T11:30:00Z, ORD-12345, OPER-001, MANUFACTURING_STARTED, PRICE_CALCULATED, MANUFACTURING_STARTED, 5"

**6. Интеграционные сообщения**

    timestamp, message_id, source_system, target_system, message_type, status, processing_time_ms

*Пример*: "2024-01-15T10:26:00Z, MSG-98765, MES API, CRM API, ORDER_STATUS_UPDATE, DELIVERED, 150"

**7. Ошибки API**

    timestamp, endpoint, method, status_code, error_code, request_id, user_agent

*Пример*: "2024-01-15T10:35:00Z, /api/orders/12345, GET, 500, INTERNAL_SERVER_ERROR, REQ-ABCD, curl/7.68.0"

## 3. Уровни логирования и их использование

**DEBUG - Подробная отладочная информация**

Сценарии:

    Подробная трассировка бизнес-логики
    Параметры внутренних вызовов функций
    Состояние объектов в памяти
    Запросы к базе данных (SQL-запросы с параметрами)

*Включать*: только в dev/staging средах или при отладке конкретных проблем

**INFO - Стандартные бизнес-события**

Сценарии:

    Изменения статусов заказов
    Успешные транзакции
    Запуск/остановка сервисов
    Основные метрики производительности

*Включать*: всегда в production

**WARN - Предупреждения о потенциальных проблемах**

Сценарии:

    Медленные запросы (выше порогового значения)
    Повторные попытки (retry)
    Использование deprecated API
    Приближение к лимитам (БД, память, диски)

Включать: всегда в production

**ERROR - Ошибки, требующие внимания**

Сценарии:

    Ошибки бизнес-логики
    Ошибки интеграции с внешними системами
    Исключения в коде
    Ошибки валидации данных

Включать: всегда в production

**FATAL - Критические ошибки, приводящие к остановке**

Сценарии:

    Недоступность критических ресурсов (БД, очереди)
    Ошибки конфигурации при старте
    Утечки памяти, приводящие к падению сервиса

Включать: всегда в production

## 4. Мотивация

Проблемы, которые решит логирование:

- Снижение времени разрешения инцидентов - вместо часов/дней на анализ через клиентов -> минуты через логи
- Устранение слепых зон - понимание того, что происходит внутри систем между статусами
- Аудит и соответствие требованиям - возможность отследить все изменения в системе
- Проактивное обнаружение проблем - выявление паттернов, ведущих к ошибкам

Что даст внедрение логирования:

- Сокращение времени на реагирование с часов до минут
- Уменьшение нагрузки на техподдержку на 30-40%
- Возможность автоматического анализа частоты и типов ошибок
- Данные для улучшения UX - понимание, где пользователи сталкиваются с проблемами

Технические метрики:

- Среднее время диагностики проблем - снижение на 70%
- Количество повторяющихся инцидентов - снижение на 50%
- Время восстановления сервиса - уменьшение на 60%

Бизнес-метрики:

- Удовлетворённость клиентов - повышение на 20%
- Процент потерянных заказов - снижение на 15%
- Эффективность операторов - увеличение на 25%

## 5. Приоритезация систем для логирования и трейсинга

**Первая очередь (1-2 месяца):**

MES API - самая критичная система, отвечает за расчёт стоимости и назначение операторов

    Причина: Большинство жалоб связано с задержками и ошибками расчёта
    Логирование: Все операции расчёта, ошибки, производительность
    Трейсинг: Полный путь расчёта стоимости

Shop API - точка входа для клиентов

    Причина: Проблемы с созданием заказов и загрузкой файлов
    Логирование: Создание заказов, работа с файлами, ошибки валидации
    Трейсинг: Путь заказа от создания до передачи в MES

CRM API - управление заказами со стороны продавцов

    Причина: Проблемы с подтверждением заказов и синхронизацией статусов
    Логирование: Изменения статусов, интеграция с RabbitMQ
    Трейсинг: Взаимодействие между CRM и другими системами

**Вторая очередь (3-4 месяца):**

    Базы данных - PostgreSQL (Shop DB, MES DB)
    Message Queue - RabbitMQ
    Frontend приложения - Интернет-магазин, CRM, MES

**Третья очередь (5-6 месяцев):**

    Инфраструктура - серверы, сеть, хранилища
    Внешние интеграции - транспортные компании, платёжные системы

## 6. Предлагаемое решение

Технологический стек:

- Loki - сбор и хранение логов (Grafana Labs)
- Promtail - агент для сбора логов
- Grafana - визуализация и анализ (уже есть в стеке)
- Fluentd/Fluent Bit - альтернатива Promtail для более сложных сценариев

Компоненты для внедрения:

Loki:

    Роль: Хранение и индексация логов
    Технология: Go
    Особенности: Эффективное хранение, интеграция с Grafana

Promtail:

    Роль: Агент сбора логов на каждом сервере
    Технология: Go
    Особенности: Автообнаружение контейнеров, парсинг логов

Библиотеки логирования в каждом сервисе:

    Java: Logback с JSON-форматированием
    C#: Serilog с JSON-форматированием
    JavaScript: Winston/Pino с JSON-форматированием

Схема сбора логов:

Приложения (логи в JSON-формате) -> Promtail (на каждом хосте, сбор логов) -> Loki (хранение и поиск) -> Grafana (визуализация и анализ)

**Политика безопасности:**

Обработка чувствительных данных:

Маскирование персональной информации:

    Email: user@mail.ru -> u***@m***.ru
    Телефон: +71234567890 -> +7123*******
    Платежные карты: полная маскировка
    Адреса: частичная маскировка

Шифрование:

    Передача логов: TLS 1.3
    Хранение логов: AES-256
    Ключи шифрования: управление через KMS

Контроль доступа (RBAC):

    Уровень 1 (поддержка): Доступ к логам по order_id/customer_id
    Уровень 2 (разработчики): Доступ к логам по сервисам
    Уровень 3 (DevOps): Полный доступ к логам инфраструктуры
    Уровень 4 (архитекторы): Полный доступ ко всем логам

Аудит доступа:

    Логирование всех запросов к системе логов
    Интеграция с SIEM
    Регулярные аудиты

**Политика хранения:**

Стратегия хранения:

<pre>
┌─────────────────────────────────────────────────────────┐
│                    Хранение логов                       │
├─────────────────┬─────────────────┬─────────────────────┤
│    Hot Storage  │  Warm Storage   │    Cold Storage     │
│   (0-7 дней)    │   (8-30 дней)   │    (31-365 дней)    │
├─────────────────┼─────────────────┼─────────────────────┤
│   Loki (SSD)    │   Loki (HDD)    │    S3/Glacier       │
│   Быстрый доступ│   Средний доступ│   Архивное хранение │
│                 │                 │                     │
│   INFO, ERROR   │   Все уровни    │   Все уровни        │
│                 │                 │   (сжатие 90%)      │
└─────────────────┴─────────────────┴─────────────────────┘
</pre>

**Размеры и лимиты:**

Размер логов в день:

    Бизнес-логи: ~500 MB/день
    Логи инфраструктуры: ~200 MB/день
    Итого: ~700 MB/день или ~21 GB/месяц

Сроки хранения:

    Hot (быстрый доступ): 7 дней
    Warm (оперативный доступ): 30 дней
    Cold (архивное): 1 год
    Аудит/комплаенс: 7 лет (отдельное хранилище)

Индексы:

    По системе (mes-api, shop-api, crm-api)
    По типу (business, security, infrastructure)
    По уровню (ERROR, WARN, INFO)

**Алертинг на основе логов:**

Аномалии частоты ошибок:

    Алерт при более 10 ошибок/минуту в одном сервисе
    Алерт при более 50% увеличении ошибок за 5 минут

Аномалии в бизнес-процессах:

    Алерт при 0 новых заказов за 30 минут (возможно, сбой)
    Алерт при более 100 заказов за 1 минуту (возможно, DDoS)

Системные аномалии:

    Алерт при появлении FATAL логов
    Алерт при повторяющихся WARN логах (более 5 в минуту)

**Анализ и ML:**

Кластеризация ошибок:

    Автоматическая группировка похожих ошибок
    Выявление паттернов сбоев

Прогнозирование проблем:

    Предсказание сбоев на основе исторических данных
    Выявление сезонных паттернов

Корреляция событий:

    Связь между логами разных систем
    Выявление причинно-следственных связей

**Автоматические действия:**

При обнаружении DDoS:

        Автоматическое включение межсетевого экрана (Web Application Firewall - WAF)
        Ограничение скорости запросов
        Уведомление команде безопасности

При частых ошибках:

        Автоматический рестарт проблемного сервиса
        Перенаправление трафика на резервные инстансы
        Создание инцидента в Jira

При бизнес-аномалиях:

        Уведомление бизнес-аналитикам
        Автоматический сбор метрик для анализа
        Создание дашбордов с проблемными зонами

## 7. Критерии выбора технологии

Критерии выбора технологии логирования:

| Критерий | ELK/Elastic Stack | Loki (Grafana) | OpenSearch | Splunk | Graylog |
|----------|-------------------|----------------|------------|--------|---------|
| Лицензия | Elastic License (некоторые компоненты под SSPL) | Apache 2.0 | Apache 2.0 | Проприетарная | Apache 2.0 |
| Стоимость | Бесплатно для базового, платно для расширенных функций | Полностью бесплатно | Полностью бесплатно | Очень дорого ($1500/GB/день) | Бесплатно |
| Интеграция с Grafana | Хорошая (через плагин) | Отличная (родная интеграция) | Хорошая (через плагин) | Ограниченная | Хорошая |
| Производительность | Высокая, но требовательна к ресурсам | Высокая, оптимизирована для логов | Высокая, форк Elasticsearch | Очень высокая | Средняя |
| Масштабируемость | Отличная | Хорошая (до средних нагрузок) | Отличная | Отличная | Хорошая |
| Простота развертывания | Сложная | Простая (однобинарный файл) | Средняя | Сложная | Средняя |
| Поддержка облаков | Отличная (Elastic Cloud) | Хорошая | Хорошая (AWS OpenSearch Service) | Отличная | Хорошая |
| Экосистема | Очень богатая | Растущая (часть Grafana Stack) | Растущая (форк ELK) | Очень богатая | Средняя |
| Безопасность | Продвинутая (платно) | Базовая (SSL, аутентификация) | Хорошая | Очень продвинутая | Хорошая |
| Сообщество | Огромное | Большое и растущее | Большое | Большое (но коммерческое) | Среднее |

**Обоснование выбора Loki:**

Плюсы Loki:

    Бесплатность и открытость - Apache 2.0 лицензия, нет скрытых платежей
    Отличная интеграция с Grafana - уже выбранной для мониторинга
    Простота развертывания и управления - важно для маленькой команды
    Эффективное хранение - индексирует только метаданные, логи хранятся в сжатом виде
    Низкие требования к ресурсам - важно при ограниченном бюджете

Минусы Loki:

    Меньшая функциональность по сравнению с Elasticsearch
    Ограниченные возможности полнотекстового поиска
    Меньшее сообщество чем у ELK

Почему выбрали Loki:

    Уже используем Grafana для мониторинга и трейсинга - естественная интеграция
    Маленькая команда - простота управления критически важна
    Ограниченный бюджет - не можем позволить платные решения
    Средний объем логов (~700 MB/день) - Loki хорошо справляется
    Единая платформа - один интерфейс (Grafana) для метрик, трейсов и логов

Альтернативный план (если Loki не справится):

    Краткосрочно (1-2 года): Loki
    При росте объема (более 5 GB/день): Миграция на OpenSearch
    При требовании продвинутого анализа: Добавление Elasticsearch для аналитики
