# Архитектурное решение по трейсингу

## 1. Анализ системы и точек уязвимости

**Критические точки, где заказ может "сломаться" или зависнуть:**

Передача 3D-файла (Интернет-магазин -> Shop API -> S3)

    Риск потери файла при загрузке
    Недостаточное пространство в хранилище
    Ошибки валидации файла

Расчёт стоимости (Shop API -> Messages Queue -> MES API)

    Потеря сообщения в очереди
    Таймаут расчёта (30+ минут)
    Ошибки расчёта из-за сложности модели

Подтверждение производства (CRM API -> Messages Queue -> CRM)

    Потеря сообщения о подтверждении
    Конфликты статусов между системами
    Человеческий фактор (продавец не подтвердил)

Работа оператора (MES -> MES API -> MES DB)

    Долгая загрузка интерфейса
    Потеря назначения заказа
    Ошибки обновления статуса

Синхронизация статусов (RabbitMQ между всеми системами)

    Потеря сообщений о смене статуса
    Разные версии схемы сообщений
    Обработка дубликатов сообщений

## 2. Данные для трейсинга

**Обязательные данные для каждого трейса:**

Контекст трейса:

    trace_id - уникальный идентификатор трейса
    span_id - идентификатор спэна
    parent_span_id - родительский спэн
    timestamp - время события
    duration - длительность операции

Бизнес-контекст:

    order_id - идентификатор заказа
    customer_id - идентификатор клиента
    order_status - текущий статус заказа
    order_type - тип заказа (готовый/на заказ)
    model_complexity - сложность 3D-модели

Технический контекст:

    service_name - имя сервиса
    host_name - хост
    http_method - HTTP метод (если применимо)
    http_status - HTTP статус
    endpoint - эндпоинт API
    queue_name - имя очереди (если применимо)
    message_id - идентификатор сообщения

Метаданные операций:

    file_size - размер 3D-файла
    calculation_time - время расчёта стоимости
    error_message - сообщение об ошибке (если есть)
    retry_count - количество попыток повторной обработки
    user_role - роль пользователя, инициировавшего операцию

## 3. Мотивация

**Почему трейсинг необходим для "Александрита":**

Бизнес-проблемы, которые решит трейсинг:

- Потерянные заказы - Трейсинг покажет, на каком этапе исчезает заказ и почему.
- Неопределённые статусы - Позволит увидеть полный путь заказа и идентифицировать, где статус не обновился.
- Длительные простои - Выявит этапы, на которых заказы зависают на длительное время.
- Проблемы с синхронизацией - Покажет расхождения в статусах между системами.

Что даст внедрение трейсинга:

- Снижение времени диагностики проблем с заказами с часов до минут
- Возможность проактивного обнаружения заторов в процессе обработки
- Прозрачность сквозных бизнес-процессов для всех стейкхолдеров
- Данные для оптимизации наиболее проблемных этапов

**Технические и бизнес-метрики, на которые повлияет трейсинг:**

Технические метрики:

- Среднее время обработки заказа на каждом этапе
- Процент потерянных/зависших сообщений в очередях
- Количество ретраев и их причины
- Распределение времени расчёта стоимости по сложности моделей

Бизнес-метрики:

- Общее время выполнения заказа (от создания до доставки)
- Процент заказов, зависших на каждом этапе
- Среднее время подтверждения заказа продавцом
- Процент заказов с расхождениями статусов между системами

## 4. Предлагаемое решение

**Архитектура трейсинга:**

Технологический стек:

- OpenTelemetry - стандарт для сбора телеметрии
- Jaeger - для хранения и запросов трейсов
- OpenTelemetry collector - для приёма и обработки трейсов
- Grafana - для визуализации и алертинга
- Kafka - для буферизации трейсов (опционально, для высокой нагрузки)

**Компоненты для внедрения:**

Instrumentation всех сервисов:

- Java-сервисы: OpenTelemetry Java Agent/Spring Boot Starter
- C# сервисы: OpenTelemetry .NET
- Frontend: OpenTelemetry JavaScript
- Базы данных: инструментирование драйверов/запросов
- RabbitMQ: трассировка сообщений через заголовки

Сервисы трейсинга:

- OpenTelemetry collector (приём трейсов)
- Jaeger (хранение и запросы)
- Grafana (визуализация и алертинг)

Интеграции:

- Связь с системой мониторинга (Prometheus)
- Интеграция с логами (Loki)
- Экспорт в SIEM для безопасности

Контекстная передача:

- HTTP-запросы: Передача traceparent заголовка
- Сообщения RabbitMQ: Встраивание контекста в заголовки сообщений
- Базы данных: Инструментирование драйверов для трассировки запросов
- Внешние вызовы: Трассировка API-вызовов к внешним сервисам

## 5. Компромиссы

**Ситуации, когда трейсинг не принесёт пользы или невозможен:**

Унаследованные или проприетарные системы:

MES система куплена с исходным кодом, но может использовать устаревшие технологии<br>
Инструментирование может потребовать модификации ядра системы<br>
*Оценка:* 2-3 месяца работы C# разработчика

Высоконагруженные операции:

Трейсинг каждого расчёта стоимости может создать значительную нагрузку<br>
*Компромисс:* семплирование (только 10% самых долгих расчётов)<br>
*Оценка дополнительной нагрузки:* +5-15% к CPU

Быстрые операции:

Трейсинг простых HTTP-запросов может быть дороже самой операции<br>
*Решение:* не трассировать healthcheck и статические эндпоинты<br>
*Порог:* операции быстрее 10мс не трассируются

Ограничения хранилища:

Хранение полных трейсов для всех заказов за 30 дней может быть дорого<br>
*Компромисс:* хранить детальные трейсы 7 дней, агрегированные метрики - 30 дней<br>
*Ориентировочная стоимость:* ?????? руб/мес за хранилище

Контекст в асинхронных операциях:

Правильная передача контекста в RabbitMQ требует модификации всех производителей/потребителей<br>
*Риск:* частичная трассировка при отсутствии контекста<br>
*Решение:* поэтапное внедрение с контролем качества

## 6. Аспекты безопасности

Меры безопасности для системы трейсинга:

Контроль доступа:

    Аутентификация через OAuth2/OpenID Connect

Ролевая модель доступа:

    support - только просмотр трейсов по order_id
    developer - доступ к поиску и анализу
    architect - полный доступ, включая конфигурацию
    auditor - доступ только на чтение для compliance

Защита данных:

    Маскирование PII (Personal Identifiable Information) в трейсах
    Шифрование трейсов при передаче (TLS 1.3)
    Шифрование данных при хранении
    Автоматическое удаление трейсов через 30 дней

Сетевая безопасность:

    OpenTelemetry Collector доступен только из внутренней сети
    Jaeger UI доступен только через VPN или корпоративный портал
    Ограничение доступа по IP-адресам

Мониторинг безопасности:

    Аудит доступа к данным трейсинга
    Алёрты на подозрительные запросы (много запросов по разным order_id)
    Интеграция с SIEM для корреляции событий

Соответствие требованиям:

    GDPR compliance: право на удаление данных
    Логирование всех операций с трейсами
    Регулярные security-аудиты системы

## 7. Автоматический мониторинг и алертинг

**Система алертинга на основе трейсов:**

Мониторинг времени прохождения этапов:

    Алерт, если заказ находится в статусе PRICE_CALCULATED более 1 часа
    Алерт, если подтверждение продавцом занимает более 4 часов
    Алерт, если производство занимает более 48 часов

Обнаружение потерянных заказов:

    Алерт, если заказ не менял статус более 24 часов
    Алерт, если заказ исчез из трейсинга (нет завершающего спэна)
    Алерт, если статусы в разных системах расходятся более 1 часа

Анализ паттернов ошибок:

    Алерт, если более 5% заказов падают на одном этапе
    Алерт, если время расчёта стоимости выросло на 50%
    Алерт, если очередь расчётов превышает 100 сообщений

Техническая реализация:

Grafana с плагином для Jaeger:

    Дашборды для мониторинга потока заказов
    Графики времени выполнения этапов
    Heatmap распределения ошибок

Пользовательские алерты на основе трейсов:

    Использование Jaeger API для запроса метрик
    Интеграция с Alertmanager для уведомлений
    Автоматическое создание тикетов в Jira при обнаружении проблем

Автоматические действия:

    При обнаружении зависшего расчёта - автоматический ретрай
    При расхождении статусов - запуск процедуры синхронизации
    При высокой очереди - уведомление об увеличении мощностей
